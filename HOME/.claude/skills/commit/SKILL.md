# Smart Commit: 意味ごとの自動分割コミット

ステージ済みの変更を分析し、論理的に関連する変更をグループ化して、依存関係順に個別のコミットを作成する。

## ワークフロー

### Step 0: チケットIDの特定

コミットメッセージに含めるチケットIDを以下の順で取得する。見つかった時点で確定する。

**1. ブランチ名からパース**

```bash
git branch --show-current
```

以下のようなパターンからIDを抽出する:
- `feature/PROJ-123-add-login` → `PROJ-123`
- `fix/42-null-check` → `#42`
- `issue-789-refactor` → `#789`
- Jira形式（`[A-Z]+-\d+`）はそのまま、数字のみの場合は `#` を付ける

**2. GitHub Issueから取得**

ブランチ名からIDが取れない場合、`gh` CLIで関連Issueを確認する:

```bash
gh pr view --json number --jq '.number' 2>/dev/null
```

PRに紐づくIssueがあればそのIDを使用する。

**3. ユーザーに確認**

上記のいずれでもIDが特定できない場合（masterブランチ等）、ユーザーに確認する:
- チケットIDがあれば入力してもらう
- なければIDなしでコミットするか確認する

### Step 1: ステージ済み変更の収集

ステージ済みの変更を取得する。

```bash
git diff --cached --name-status
git diff --cached
```

ステージ済みの変更がない場合は、その旨をユーザーに伝えて終了する。

### Step 2: 変更の意味分析

差分を読み、各変更を「意味単位」に分類する。意味単位とは、一つの目的や意図でまとまる変更のこと。

**分類の観点：**

- **機能単位**: 同じ機能に関連するファイル群（例: ある機能の実装とそのテスト）
- **変更の種類**: バグ修正、新機能、リファクタリング、ドキュメント更新など
- **影響範囲**: 設定ファイルの変更、依存関係の更新、コードの変更

**1ファイル内に複数の意味がある場合：**

1ファイルに異なる目的の変更が混在している場合は、ファイル全体を最も支配的な変更グループに含める。
`git add -p` によるhunk分割は行わない（安全性のため）。

**判断に迷ったら：**

関連性が不明確な変更は、同じコミットにまとめてよい。過剰な分割よりも、適切な粒度を優先する。
目安として、一つのコミットメッセージで自然に説明できる範囲を1コミットとする。

### Step 3: コミット順序の決定

依存関係に基づいて順序を決める。

**順序の原則：**
1. インフラ・設定の変更（.gitignore、設定ファイル等）
2. 依存関係の追加・更新
3. リファクタリング（既存コードの整理）
4. バグ修正
5. 新機能の追加
6. ドキュメントの更新
7. テストの追加・修正

これは目安であり、実際の依存関係を見て判断する。例えば新機能が先にないとテストが書けない場合は、新機能を先にコミットする。

### Step 4: 順次コミットの実行

各グループについて、以下を実行する。

1. 一旦すべてのステージを解除する（最初のグループ処理前に1回だけ）:
   ```bash
   git reset HEAD
   ```

2. 対象ファイルだけをステージする:
   ```bash
   git add <file1> <file2> ...
   ```

3. コミットメッセージを作成してコミットする:
   ```bash
   git commit -m "$(cat <<'EOF'
   <type>: <ticket-id> <subject>

   <body（必要な場合）>

   Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
   EOF
   )"
   ```
   チケットIDが特定できなかった場合（ユーザーが「なし」を選択）は `<ticket-id>` 部分を省略する。

### Step 5: 結果の報告

すべてのコミット完了後、作成されたコミットの一覧を表示する:

```bash
git log --oneline -<コミット数>
```

## コミットメッセージ規約

プロジェクトの `commit.schema.md` が存在する場合はそれに従う。
存在しない場合は以下のデフォルトを使用する:

- **言語**: 日本語
- **形式**: `<type>: <ticket-id> <subject>`（IDなしの場合は `<type>: <subject>`）
- **type**: feat / fix / docs / style / refactor / chore / test
- **subject**: 50文字以内、末尾に句点なし
- **body**: 任意。変更の理由や背景があれば記述（1行72文字以内）
- **末尾**: `Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>`

## 注意事項

- `--no-verify` は使わない。pre-commitフックが失敗した場合は原因を調査する
- `.env` や認証情報を含むファイルはコミットしない。発見した場合はユーザーに警告する
- ステージ済みの変更のみを対象とする。未ステージの変更には触れない
- `git add -p`（対話的な部分ステージ）は使わない。ファイル単位でステージする
- force pushは行わない

## 例

### 例1: ブランチ `feature/PROJ-123-auth` で設定+新機能が混在

ステージ済みの変更:
- `.gitignore` の追加
- `src/auth.py` の追加
- `tests/test_auth.py` の追加

チケットID: `PROJ-123`（ブランチ名から取得）

分割結果:
1. `chore: PROJ-123 .gitignoreを追加` → `.gitignore`
2. `feat: PROJ-123 ユーザー認証機能を追加` → `src/auth.py`, `tests/test_auth.py`

### 例2: ブランチ `fix/42-null-check` でリファクタリングとバグ修正

ステージ済みの変更:
- `src/utils.py` の関数名リネーム
- `src/api.py` の関数名リネーム（utilsに追従）
- `src/handler.py` のnullチェック追加

チケットID: `#42`（ブランチ名から取得）

分割結果:
1. `refactor: #42 utils関数名をsnake_caseに統一` → `src/utils.py`, `src/api.py`
2. `fix: #42 handlerのnullポインタエラーを修正` → `src/handler.py`

### 例3: masterブランチでIDなし

チケットIDが特定できない → ユーザーに確認 → 「なし」を選択

分割結果:
1. `docs: READMEを更新` → `README.md`
